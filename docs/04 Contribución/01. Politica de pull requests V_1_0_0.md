# 01. Politica de pull requests V_1_0_0

## 1. Propósito

Este documento define la política de revisión y mergeo de pull requests (PR) para el proyecto EcoLogística Lima. Aplica a todas las contribuciones que se integran en la rama `main`.

## 2. Estados del PR

| Estado | Descripción |
|---|---|
| **Draft** | El PR está en preparación. No está listo para revisión. Se usa para trabajo en progreso. |
| **Ready for Review** | El PR está completo y listo para revisión humana. Requiere auditoría técnica independiente previa. |
| **Approved** | El PR tiene al menos una aprobación humana de alguien distinto del autor y todos los checks en verde. |

## 3. Proceso de revisión

El proceso de revisión consta de tres etapas distintas. Ninguna etapa sustituye a las otras.

### 3.1 Autorrevisión del implementador

Antes de marcar un PR como "Ready for Review", el autor debe completar:

1. Revisar que los cambios cumplen el objetivo del ticket Jira.
2. Verificar que no se introducen secretos, credenciales ni datos sensibles.
3. Confirmar que las pruebas unitarias y de integración pasan localmente.
4. Ejecutar lint, type-check y formateo según corresponda.
5. Completar la plantilla de PR con toda la información requerida.

La autorrevisión es un paso necesario pero **no sustituye** la auditoría técnica independiente.

### 3.2 Auditoría técnica independiente

Antes de la revisión humana, la auditoría técnica puede ser realizada por:

- Una persona distinta del autor, o
- Una sesión independiente de IA que inspeccione directamente los archivos y la evidencia.

La sesión implementadora no puede aprobar su propio trabajo. La aprobación final sigue siendo humana y de alguien distinto del autor.

La auditoría técnica incluye:

1. Verificación de que los cambios cumplen el objetivo del ticket Jira.
2. Revisión de la arquitectura y convenciones de código.
3. Verificación de que las pruebas son adecuadas y suficientes.
4. Identificación de riesgos técnicos o de seguridad.
5. Documentación de hallazgos en el PR.

La auditoría técnica **no sustituye** la aprobación humana final.

### 3.3 Aprobación humana

El PR requiere al menos una aprobación humana de alguien distinto del autor. La aprobación confirma que:

1. El PR ha sido auditado técnicamente.
2. Los checks están en verde.
3. Las alertas de CodeQL han sido revisadas.
4. No hay riesgos críticos sin mitigar.

## 4. Requisitos para mergeo

Un PR puede mergearse a `main` únicamente cuando se cumplen **todas** las condiciones:

| # | Requisito | Tipo | Estado |
|---|---|---|---|
| 1 | PR abierto y no Draft | Requisito | Pendiente de verificar |
| 2 | Head igual al auditado y aprobado | Requisito | Pendiente de verificar |
| 3 | Evidencia de checks correspondientes a ese head o al merge commit asociado | Requisito | Pendiente de verificar |
| 4 | Nueva auditoría de los cambios afectados si cambia el head | Requisito | Pendiente de verificar |
| 5 | Al menos una aprobación humana de alguien distinto del autor | Requisito | Pendiente de verificar |
| 6 | CI (todos los jobs) completado correctamente | Requisito | Pendiente de verificar |
| 7 | CodeQL / Python completado correctamente | Requisito | Pendiente de verificar |
| 8 | CodeQL / JavaScript-TypeScript completado correctamente | Requisito | Pendiente de verificar |
| 9 | Revisión explícita de alertas CodeQL documentada en el PR | Requisito | Pendiente de verificar |
| 10 | Todas las conversaciones del PR resueltas | Requisito | Pendiente de verificar |
| 11 | Rama actualizada con `main` cuando corresponda | Requisito | Pendiente de verificar |
| 12 | Sin force push ni eliminación de `main` | Requisito | Pendiente de verificar |

### 4.1 Clasificación interna de auditoría

El proyecto utiliza una clasificación interna de hallazgos de auditoría. Esta clasificación es independiente de las severidades originales de CodeQL y se aplica a todos los hallazgos pendientes de la auditoría, no solamente a CodeQL.

| Clasificación interna | Descripción | Justificación |
|---|---|---|
| **BLOCKER** | Vulnerabilidad explotable o fallo crítico que compromete la seguridad o integridad del sistema. | Requiere remediación inmediata antes de mergear. |
| **HIGH** | Vulnerabilidad con alto impacto potencial o fallo grave de arquitectura. | Requiere remediación antes de mergear. |
| **MEDIUM** | Vulnerabilidad con impacto moderado o fallo de convenciones de código. | Requiere remediación o justificación aceptada por revisión independiente. |
| **LOW** | Menor riesgo o mejora recomendada. | No bloquea el merge. Puede planificarse para remediación posterior. |
| **NOTE** | Observación informativa sin impacto en seguridad o funcionalidad. | No bloquea el merge. |

Se conservan tanto el nivel original del resultado de CodeQL como su severidad de seguridad, cuando esté disponible. La clasificación interna BLOCKER/HIGH/MEDIUM/LOW/NOTE se documenta por separado, con justificación basada en el impacto.

### 4.2 Gate de hallazgos pendientes

> **Importante**: Un job CodeQL en verde **no** prueba ausencia de vulnerabilidades. Significa únicamente que el análisis se ejecutó correctamente.

El gate de hallazgos pendientes de la auditoría es:

| Clasificación interna | Valor requerido |
|---|---|
| BLOCKER | 0 |
| HIGH | 0 |
| MEDIUM | 0 |

- Un hallazgo BLOCKER, HIGH o MEDIUM pendiente **impide el merge**.
- Un plan de remediación por sí solo **no autoriza el merge**.
- Los falsos positivos requieren justificación y revisión independiente.

### 4.3 Revisión de alertas CodeQL

El revisor debe:

1. Acceder a **Security > Code scanning alerts** en el repositorio.
2. Verificar si el PR introduce alertas nuevas.
3. Documentar en el PR:
   - "No se introducen alertas nuevas" (con captura o referencia), o
   - Listado de alertas nuevas con justificación de aceptación o plan de remediación.

## 5. Revalidación del head

Antes de mergear, se debe revalidar que:

1. El head del PR está actualizado con `main`.
2. Los checks se ejecutaron sobre el commit más reciente.
3. No hubo cambios posteriores a la última ejecución de checks.

Si `main` avanzó después de la última ejecución, el autor debe actualizar la rama y esperar nueva ejecución de checks.

## 6. Nuevos cambios después de revisión

Si el autor realiza cambios después de una revisión o aprobación:

1. La aprobación previa queda invalidada (dependiendo de la configuración de GitHub).
2. Se requiere nueva revisión humana.
3. Se requiere nueva ejecución de checks sobre el nuevo head.
4. Se requiere nueva auditoría de los cambios afectados.

## 7. Restricciones técnicas

| Restricción | Descripción |
|---|---|
| **Force push** | Prohibido en `main`. Prohibido en ramas de PR si invalidan revisiones. |
| **Eliminación de main** | Prohibida. |
| **Auto-aprobación** | Prohibida. El autor no puede aprobar su propio PR. |
| **Mergeo sin checks** | Prohibido. Todos los checks deben estar en verde. |

## 8. Configuración recomendada para `main` (GitHub Settings)

La configuración y verificación de protección de main forma parte de ECL-35 y requiere una acción posterior del administrador en GitHub. Esta implementación local no modifica Settings.

| Configuración | Valor recomendado | Tipo | Estado |
|---|---|---|---|
| Require pull request before merging | Habilitado | Recomendación | Pendiente de verificar |
| Require approvals | 1 | Recomendación | Pendiente de verificar |
| Dismiss stale pull request approvals when new commits are pushed | Habilitado | Recomendación | Pendiente de verificar |
| Require status checks to pass before merging | Habilitado | Recomendación | Pendiente de verificar |
| Status checks requeridos | Ver tabla 8.1 | Recomendación | Pendiente de verificar |
| Require conversation resolution before merging | Habilitado | Recomendación | Pendiente de verificar |
| Require branches to be up to date before merging | Habilitado | Recomendación | Pendiente de verificar |
| Block force pushes | Habilitado | Recomendación | Pendiente de verificar |
| Allow deletions | Deshabilitado | Recomendación | Pendiente de verificar |

### 8.1 Nombres de jobs

Los nombres de jobs definidos en los workflows son:

| Workflow | Job |
|---|---|
| CI | Backend / Quality and unit |
| CI | Backend / Integration |
| CI | Frontend |
| CodeQL | CodeQL / Python |
| CodeQL | CodeQL / JavaScript-TypeScript |

Los contextos exactos seleccionados como required checks se confirmarán en GitHub tras su ejecución.

## 9. Ramas de evidencia

Según la coordinación del proyecto, se preservan ramas de evidencia para auditoría. Las ramas que contengan evidencia de análisis de seguridad o revisiones de código no deben eliminarse sin autorización del coordinador.

## 10. Excepciones

No se contemplan excepciones a esta política. Cualquier situación no cubierta debe elevarse al coordinador del proyecto.
