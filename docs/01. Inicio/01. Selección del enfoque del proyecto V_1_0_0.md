## 1. Introducción y Contexto

El proyecto **EcoLogística Lima** busca desarrollar una plataforma web moderna que optimice las rutas de reparto de última milla para la empresa logística *DistriRápido S.A.C.*, ubicada en San Juan de Lurigancho, Lima. 

El proyecto enfrenta desafíos complejos de ingeniería que incluyen:
- Optimización multiobjetivo (distancia, tiempo, emisiones, cumplimiento de ventanas de tiempo)
- Aplicación de metaheurísticas avanzadas (Algoritmos Genéticos, ACO, Búsqueda Tabú)
- Integración con APIs de tráfico en tiempo real
- Consideraciones de sostenibilidad ambiental y social
- Restricciones normativas y geográficas específicas de Lima

Dada esta complejidad, la **selección del enfoque de gestión de proyectos** es crítica para el éxito del proyecto.

## 5. Decisión y Justificación del Enfoque Seleccionado

### **ENFOQUE SELECCIONADO: HÍBRIDO (Scrumfall)**

#### 5.1 Definición del Enfoque Híbrido

El enfoque **Híbrido Adaptativo (Scrumfall)** combina:
- **Fase Predictiva Inicial (Inicio y Planificación):** Estructura clara de requisitos, arquitectura y riesgos
- **Ciclos Iterativos Ágiles (Ejecución):** Sprints de 2-3 semanas con entregables incrementales
- **Cierre Estructurado:** Documentación y evaluación formal al final de cada iteración

**Alineación PMBOK 8ª Edición:**
- Reconoce el proyecto como **altamente complejo** → Requiere enfoque adaptativo
- Respeta **restricciones de negocio** (presupuesto, tiempo) → Requiere planificación base
- Incorpora **12 competencias de gestión** del estándar moderno
- Aplica **gestión del cambio proactiva** integrada en cada sprint

#### 5.2 Justificación por Variable

| Variable | Decisión Justificada |
|----------|---------------------|
| **Claridad de Requisitos** | Requerimientos funcionales definidos (RF-01 a RF-10), pero requieren validación iterativa con stakeholders |
| **Estabilidad** | Se esperan cambios en APIs de tráfico y normativa → Sprints permiten adaptación ágil |
| **Complejidad Técnica** | Algoritmos de optimización requieren experimentación → Iteraciones son esenciales |
| **Riesgo Técnico** | Desempeño algorítmico incierto → Pruebas de rendimiento en cada sprint |
| **Flexibilidad** | Cambios en requisitos de sostenibilidad → Sprints de 2-3 semanas adaptan cambios |
| **Experiencia** | Equipo con experiencia Python/React, pero nueva en VRP/metaheurísticas → Mentoring y learning-by-doing |
| **Tiempo** | 14 semanas fijadas → 4 iteraciones con entregas puntuales |
| **Innovación** | Algoritmos Green VRP son nuevos → Ciclos cortos permiten exploración |

#### 5.3 Mapeo a Cronograma del Proyecto

```
PREDICTIVO (Semana 0-1)         ÁGIL ITERATIVO (Semanas 2-14)
├── Análisis Profundo           ├── SPRINT 1 (Semanas 2-4): Gestión Flota & Pedidos
├── Diseño Arquitectónico       ├── SPRINT 2 (Semanas 5-7): Algoritmo Básico & Pruebas
├── Identificación Riesgos      ├── SPRINT 3 (Semanas 8-11): Mapas, Dashboard, Reportes
└── Planificación Base           └── SPRINT 4 (Semanas 12-14): Optimización & Cierre

En cada Sprint:
- Daily standups (15 min)
- Review al final (60 min)
- Retrospectiva (45 min)
- Ajuste de backlog según cambios reales
```

## 7. Riesgos del Enfoque y Mitigación

| Riesgo | Probabilidad | Impacto | Estrategia de Mitigación |
|--------|-------------|--------|--------------------------|
| Over-engineering en fase predictiva | Media | Alto | Timeboxing: máx 2 semanas en análisis |
| Scope creep en sprints | Alta | Alto | Product Backlog refinado cada semana |
| Cambios en API Waze/Google Maps | Alta | Medio | Abstracción de capas de datos, pruebas mock |
| Equipo sin experiencia en metaheurísticas | Alta | Alto | Capacitación en semana 1, pair programming |
| Presión de tiempo (14 semanas fijas) | Alta | Alto | MVP claro (70% de RF), resto = fase 2 |
