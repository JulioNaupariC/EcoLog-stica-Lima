## 1. Introducción y Contexto

### 1.1 Importancia de Gestión de Interesados

La **gestión de interesados** es crítica en EcoLogística Lima porque:
- ✅ Proyecto tiene **múltiples grupos con intereses divergentes** (cliente, conductores, reguladores, equipo)
- ✅ Cada grupo tiene **poder diferente** para afectar proyecto (pueden bloquearlo, acelerar, sabotear)
- ✅ **Comunicación incorrecta** puede causar: rechazo del sistema, retrasos, conflictos
- ✅ **Soporte activo** de interesados clave es crítico para adopción (conductores, coordinador flota)

### 1.2 Definiciones

- **Interesado (Stakeholder):** Cualquier persona, grupo u organización que afecta o es afectada por el proyecto
- **Poder:** Capacidad de influir decisiones o bloquear proyecto
- **Interés:** Nivel de preocupación sobre el proyecto y sus resultados
- **Matriz Poder/Interés:** Herramienta de segmentación para estratificar comunicación

## 5. Análisis de Riesgos por Grupo de Stakeholders

### 5.1 Principales Riesgos de Gestión de Interesados

| Riesgo | Stakeholder Afectado | Probabilidad | Impacto | Mitigación |
|--------|------|---|-|-|
| **Rechazo de conductores** | STK-12,13 | Alta | Crítico (adoption falla) | Diseño participativo Sem 1-2, iteración rápida de UI |
| **Cambio de prioridades cliente** | STK-10, STK-11 | Media | Alto (scope creep) | Scope freeze Sem 4, Change Request formal |
| **Falta de datos de DistriRápido** | STK-10, STK-11 | Media | Crítico (algoritmo no entrena) | Datos sintéticos, fallback a benchmarks |
| **Cambios normativos (MTC)** | STK-20 | Media | Medio (requiere ajustes) | Arquitectura flexible, monitoreo semanal |
| **Falta de disponibilidad instructor** | STK-09 | Baja | Medio (evaluación retrasada) | Documentación clara, escalación al programa |
| **Presión de equipo por tiempo** | STK-01-08 | Alta | Medio (burnout) | Gestión ágil de workload, days-off respetados |
| **Conflictos técnicos (Líder vs. Devs)** | STK-02, STK-03,04 | Baja | Medio (bloqueos técnicos) | Code review colaborativo, decisiones documentadas |

### 5.2 Plan de Contingencia por Riesgo Crítico

**Si conductores rechazan sistema (SUS <70):**
1. Escalación inmediata a PO y Sponsor
2. Rediseño de UI en máx 1 semana
3. Validación con conductores nuevamente
4. Si sigue bajo: MVP scope reducido (100 pedidos), lanzamiento fase 2 con UI mejorada

**Si cliente cambia prioridades de features:**
1. PM propone Change Request formal
2. Sponsor aprueba/rechaza (máx 24h)
3. Si aprobado: replanificar backlog, ajustar cronograma si es necesario
4. Goal: no más de 1 cambio mayor por sprint
